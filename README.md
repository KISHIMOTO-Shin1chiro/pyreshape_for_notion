# pyreshape_for_notion (English)

A Python library for migrating conversation histories from ChatGPT, Claude, and Gemini into Notion as cleanly formatted Markdown.

## Motivation

I have been using ChatGPT, Claude, and Gemini, the three major frontier AI services, primarily as research tools. As the years pass, a substantial volume of textual data accumulates in each account. To manage this data efficiently and to keep it visible in a form that I can actually use when I need it, I came to the conclusion that a periodic migration into Notion is currently the most effective approach available to me.

When I started doing this migration by hand, I quickly realised how much effort and time it consumed. On top of that, the structural elements that Notion supports under its enhanced Markdown dialect, document hierarchy, TeX equations, tables, and code blocks in various languages (Python, Mermaid, and so on), were often not preserved when I exported chats and tried to import them. Fixing this by hand inside Notion turned out to be impractical at scale.

`pyreshape_for_notion` is the library I built to solve this problem. It absorbs the format-specific quirks of each AI service's export, restores the structural elements that Notion expects, and produces zip batches ready to be imported into Notion in one step.

## Supported AI services

- **ChatGPT**, processed from the official `conversations.json` export, including GPT-5 series messages that split a single answer across multiple `assistant(text)` chunks, tool-use traces (web search, code interpreter), citation markers, and LaTeX delimiters.
- **Claude**, processed from the official `conversations.json` export, including extended-thinking traces.
- **Gemini**, processed from Markdown files generated by browser extensions such as the AI Chat Exporter.

## Glossary of project-specific terms

`pyreshape_for_notion` uses a small number of internal terms consistently. Reading them once here saves time later.

- **prompting–completing pair**, abbreviated **pcp**. One exchange consisting of a user message and the AI's reply to it. The library treats the pcp as the atomic unit of a conversation when splitting long chats into smaller files.
- **pcp number**. A three-digit sequence number assigned to each pcp within a conversation, written as `pcp_001`, `pcp_002`, and so on. When a user message contains an explicit label of this form, the library preserves it; otherwise a number is generated automatically.
- **pcp date**. The creation date of a pcp, used for ordering and for the date prefix in generated filenames.
- **normalized conversation**, abbreviated as the type `NormalizedConv`. The platform-neutral representation a conversation takes once a service-specific parser has finished with it. Downstream stages of the pipeline (Notion MD generation, splitting, zipping) operate exclusively on `NormalizedConv` objects, which is how the library keeps platform-specific logic isolated.
- **DriveLayout**. The single source of truth for folder naming under a `base_dir`. Defined in `pyreshape_for_notion.core.layout`. Folder names are numbered in the order they are produced by the pipeline; only one place in the codebase needs to change if the naming scheme is revised.
- **readable filename**. The human-friendly filename assigned to a renamed Notion Markdown file, in the form `{YYYY-MM-DD}__{sanitized_title}__{first8_of_conv_id}.md`. The trailing 8 characters of the conversation id are kept to guarantee uniqueness across collisions.

## Design philosophy

The codebase is organised around a hub-and-spoke pattern. Each AI service has a thin parser whose only job is to read the platform's export format and emit a `NormalizedConv`. From that point on, all further processing happens in the platform-neutral `core` module. This means that adding a new platform is, in principle, a matter of writing a single new parser, and that improvements to the shared pipeline benefit all platforms at once.

Folder layout is treated as part of the public contract. Each pipeline stage writes to its own folder under `base_dir`, named with a leading sequence number so the order of operations is visible at a glance. The entire numbering scheme is centralised in one module so that revisions are cheap and traceable.

## Usage in Google Colab

### Step 1. Mount Google Drive

```python
from pyreshape_for_notion.core import drive_io
my_drive = drive_io.mount_google_drive()
```

### Step 2. Place raw export files

Put the raw export from each service in the `0_raw_export` subfolder of the corresponding `base_dir`. For example:

- Claude: `My Drive/AI_Services/Conversation_History/1_Claude/0_raw_export/conversations.json`
- ChatGPT: `My Drive/AI_Services/Conversation_History/2_ChatGPT/0_raw_export/conversations-*.json`
- Gemini: `My Drive/AI_Services/Conversation_History/3_Gemini/0_raw_export/*.md`

### Step 3. Run a full export

```python
from pyreshape_for_notion import claude
base_dir = my_drive / "AI_Services/Conversation_History/1_Claude"
result = claude.full_export(
    raw_export_dir = base_dir / "0_raw_export",
    base_dir       = base_dir,
)
print(result)
```

The same shape of call works for `chatgpt` and `gemini`. Each platform module exposes both `full_export` (a fresh build of all outputs from scratch) and `incremental_export` (regenerate only the conversations that changed since the last run).

### Step 4. Use the lower-level API when you need finer control

```python
from pyreshape_for_notion import gemini, core
from pyreshape_for_notion.core import DriveLayout

base_dir = my_drive / "AI_Services/Conversation_History/3_Gemini"
lay = DriveLayout(base_dir)

convs = gemini.parse_folder(lay.raw_export)
core.save_notion_md(convs, lay.notion_md)
core.rename_notion_md_files(
    convs,
    source_dir=lay.notion_md,
    target_dir=lay.notion_md_renamed,
    mapping_csv_path=lay.filename_mapping_csv,
)
core.split_notion_md_files(lay.notion_md_renamed, lay.notion_md_split,
                            max_pcps_per_part=25)
core.make_zip_batches(lay.notion_md_split, lay.zip_batches,
                       target=100, overflow=20)
```

The pipeline is platform-agnostic from `core.save_notion_md` onwards, because all parsers emit the same `NormalizedConv` shape.

## Output folder layout

Under each `base_dir`, the library creates the following structure. Folder names carry leading numbers in pipeline order so the data flow is self-documenting.

```
base_dir/
├── 0_raw_export/              Inputs. Raw exports from each service.
├── 1_split_json/              Normalized conversations as JSON.
├── 2_notion_md/                Notion-flavoured Markdown, UUID-style names (pre-rename).
├── 3_notion_md_renamed/        Markdown renamed to readable filenames.
├── 4_notion_md_renamed_split/  pcp-unit splits of the renamed Markdown.
├── 5_zip_batches/              First-run zip bundles.
├── 5_zip_batches_diff/         Diff bundles produced by incremental_export.
├── 6_report/                   Analysis artefacts, including the filename mapping CSV.
│   └── filename_mapping.csv
└── _snapshot/                  Snapshot used by diff detection (operational, unnumbered).
```

Files in `3_notion_md_renamed/` follow the pattern `{YYYY-MM-DD}__{sanitized_title}__{first8_of_conv_id}.md`. For example, `2025-12-19__how_to_use_GitHub__abc12345.md`. This makes the contents recognisable at a glance once imported into Notion. The companion `6_report/filename_mapping.csv` records the original UUID-style name alongside the readable name for traceability.

## Key parameters

- `max_pcps_per_part` (default 25). Maximum number of pcps in a single split Markdown file.
- `target` / `overflow` (default 100 / 20). Target and tolerated overshoot for the number of files in a zip batch. These values reflect Notion's Markdown-import rate limit of roughly 120 files per 12 hours.
- `skip_empty` (default `True`). Whether to skip empty conversations (placeholders or deleted chats with no substantive content).
- `dedupe` (default `True`). Whether to deduplicate prompt-completion pairs within a conversation. Useful for Claude exports, which can contain branch and regeneration artefacts.
- `shift_body_headings` (default `False`). Whether to demote in-body headings by one level so they sit below the pcp heading. The default preserves the original heading levels.
- `notion_safe` (default `True`). Whether to apply the Notion-import safety cleanup. Should normally be left on.

## Generated Markdown structure

Each conversation is rendered as Markdown with the following shape (since v0.2.0; v0.4.0 added automatic Notion-safe cleanup):

```markdown
# Conversation title

## pcp_001

**A Prompt by User**

User's question.

**A Completion by LLM**

AI's reply.

---

## pcp_002
...
```

## Notion-import compatibility (v0.4.0 onward)

Claude exports occasionally contain placeholder code fences such as ``` This block is not supported on your current device yet. ``` , which mark places where an extended-thinking block or a tool-use trace would have been rendered in the Claude UI. If these are left in the Markdown, the resulting mismatched fence boundaries cause Notion's parser to refuse the entire import.

From v0.4.0, the library automatically removes these placeholders during Notion-Markdown generation. New exports do not require any special handling on the user's part.

If you have older Markdown files generated by v0.3.0 or earlier that you want to repair without regenerating from scratch, use:

```python
from pyreshape_for_notion.core import clean_notion_md_folder
stats = clean_notion_md_folder(base_dir / "4_notion_md_renamed_split")
print(stats)
```

## ChatGPT-specific handling

The ChatGPT parser includes several pieces of logic that address peculiarities of the official export.

For GPT-5 series models, a single reply is sometimes split across multiple `assistant(text)` messages in the export, with intermediate `assistant(code)` and `tool` messages between them. The library merges all `assistant(text)` chunks that fall between two consecutive user messages, so the rendered conversation contains the full reply rather than just the opening paragraph.

For replies that include web-search citations, the export embeds citation markers using Private Use Area characters (`\ue200`–`\ue202`) wrapped around tokens of the form `cite turn{N}view{M}`. These markers would otherwise show up as visible garbage text in Notion. The library strips them and lists the cited URLs at the end of each assistant turn under a dedicated references heading.

For LaTeX expressions, ChatGPT emits standard LaTeX delimiters `\(...\)` and `\[...\]`, which Notion's Markdown importer does not recognise as mathematics. The library converts these to `$...$` and `$$...$$`, which Notion renders correctly with KaTeX. ChatGPT also emits each equation a second time inside a ```` ```tex ```` (or ```` ```latex ````) fenced code block; these duplicates are removed.

## Gemini-specific handling

Gemini conversation files exported by the AI Chat Exporter use `---` (a horizontal rule) both as a conversation separator between turns and as a structural divider inside long replies (for example, before headings like `### Verification` or `### Conclusion`). The library distinguishes between these two roles by looking ahead: a `---` line is treated as a conversation separator only if the next non-empty line is `## 👤 You` or `## 🤖 Gemini`. Otherwise, it is preserved as in-body content. This restores long Gemini replies that earlier versions of the library were inadvertently splitting and partially discarding.

## Claude Artifacts to Notion (v0.6.0 onward)

For a standalone Markdown document written by Claude as an Artifact — a paper draft
full of LaTeX, for instance — rather than a chat export, use the `artifact` subpackage.

Notion's Markdown importer does not reliably interpret `$...$` / `$$...$$`. Math spans
can surface in the body as the literal string `$true$`: the delimiters survive, the LaTeX
inside them does not. Two routes are provided to avoid this.

**Route 1 — md to md** (for `Import → Text & Markdown`). Math is moved into code regions,
which the importer never parses. Nothing renders, but no LaTeX is lost.

```python
from pyreshape_for_notion import artifact
dst, stats = artifact.convert_file("paper.md")
```

**Route 2 — md to Notion API blocks** (when you want the math rendered). Bypasses the
Markdown importer: `$$...$$` becomes an `equation` block, `$...$` an `equation` rich text.
No external dependencies; plain dicts are returned.

```python
blocks  = artifact.markdown_to_blocks(text, skip_first_h1=True)
payload = artifact.make_page_payload(PARENT_PAGE_ID, artifact.extract_title(text), blocks)
# POST /v1/pages, then PATCH the remainder via artifact.chunk_blocks(blocks[100:])
```

Documents processed through route 1 are restored to real equations by route 2
(`restore_coded_math=True`, the default).

**Route 3 — upload directly (v0.7.0)**. One-stop version of route 2: reads the md,
builds the blocks, and uploads via the Notion API. Standard library only.

```python
from pyreshape_for_notion.artifact import upload_markdown
url = upload_markdown("paper.md",
                      parent_page_id="https://www.notion.so/My-Page-24c3...",  # page URL as-is
                      token="ntn_...")                                          # integration secret
```

One-time setup: create an internal integration at notion.so/my-integrations,
then add it to the parent page via ... → Connections.

# pyreshape_for_notion (日本語)

ChatGPT、Claude、Gemini の会話履歴を、整形された Markdown として Notion に移管するための Python ライブラリです。

## 動機

私は、ChatGPT、Claude、Gemini の 3 種の Frontier AI Services を、主に自身の調査研究に用いてきました。これらを使い続けていきますと、歳月が経つにつれ、莫大な量のテキストデータが各アカウント内に蓄積されていきます。それらのデータマネジメントを効率化し、データを利用したい場面でわかりやすく可視化されている状況をつくるためにどうすればよいかを考えた末、Notion への定期的なデータ移管が現状で最も有効であると結論付けました。

Notion へのデータ移管を、当初は手動でやっていたのですが、とてつもない手間と時間がかかることに気づかされました。加えて、Notion が採用している Enhanced Markdown に則った文書の階層構造、TeX 式、テーブル、コンピュータ言語によるコード類 (Python、Mermaid など) がそのまま保持されないことが多く、Notion 上でそれらを手動変更するのには限界があると悟りました。

`pyreshape_for_notion` は、この問題を解決するために作成したライブラリです。各 AI サービスのエクスポート形式に固有の癖を吸収し、Notion が想定する構造的要素を復元し、Notion に一括インポート可能な zip バッチを生成します。

## 対応 AI サービス

- **ChatGPT**: 公式エクスポート `conversations.json` を入力とし、GPT-5 系で 1 つの回答が複数の `assistant(text)` メッセージに分割されるケース、ツール使用 (web 検索、Code Interpreter) の痕跡、引用マーカー、LaTeX デリミタなどに対応しています。
- **Claude**: 公式エクスポート `conversations.json` を入力とし、拡張思考の痕跡などに対応しています。
- **Gemini**: AI Chat Exporter などのブラウザ拡張機能が生成した Markdown ファイルを入力とします。

## プロジェクト固有用語の説明

`pyreshape_for_notion` では、いくつかの独自用語を一貫した形で使っています。あらかじめここで一読いただくと、本文の理解が早くなります。

- **prompting–completing pair**、略称 **pcp**: ユーザのメッセージとそれに対する AI の返答からなる、1 つのやりとりを指します。ライブラリでは、長い会話を分割して小さなファイルにする際の最小単位として、この pcp を採用しています。
- **pcp number**: 各会話内で pcp に割り当てられる 3 桁の連番です。`pcp_001`、`pcp_002` のように表記します。ユーザのメッセージにこの形式のラベルが明示されている場合は、ライブラリがそのまま保持します。明示されていない場合は自動で番号が振られます。
- **pcp date**: pcp の作成日付です。順序付けと、生成されるファイル名の日付プレフィックスに使用されます。
- **正規化済み会話 (normalized conversation)**: 型としては `NormalizedConv`。サービス固有のパーサが処理を終えた後、会話が取るプラットフォーム中立な内部表現を指します。パイプラインの後段 (Notion MD 生成、分割、zip 化) はすべて `NormalizedConv` のみを扱うため、プラットフォーム固有のロジックがその層に漏れ出さない設計になっています。
- **DriveLayout**: `base_dir` 直下のフォルダ命名体系の単一情報源です。`pyreshape_for_notion.core.layout` で定義されています。フォルダ名はパイプラインの実行順に連番が振られており、命名規則を変更したいときは、このモジュールだけを書き換えれば済むようになっています。
- **可読ファイル名 (readable filename)**: rename 後の Notion Markdown に付与される、人間が読みやすいファイル名です。形式は `{YYYY-MM-DD}__{安全化タイトル}__{conv_id 先頭 8 文字}.md` です。末尾の conv_id 先頭 8 文字は、衝突回避を保証するために残しています。

## 設計思想

コードはハブアンドスポーク (hub-and-spoke) 構造で組まれています。各 AI サービスは、エクスポート形式を読んで `NormalizedConv` を返すだけの薄いパーサを持ちます。それ以降の処理はすべて、プラットフォーム中立な `core` モジュールで行われます。これにより、新しいプラットフォームへの対応は原理的にはパーサを 1 つ追加するだけで済み、共通パイプラインの改善は全プラットフォームに同時に波及します。

フォルダ構成も公開仕様の一部と位置づけています。パイプラインの各工程は、`base_dir` 直下の独立したフォルダに書き出します。フォルダ名には実行順を示す連番を含め、データの流れが一目で分かるようにしています。命名体系全体は 1 つのモジュールに集約されており、改訂のコストと追跡性が両立されています。

```
├── 0_raw_export/              入力。各サービスの生エクスポートを置く
├── 1_split_json/              正規化済み会話の JSON
├── 2_notion_md/               Notion 用 Markdown (UUID 系名、rename 前)
├── 3_notion_md_renamed/       rename 後の Markdown (可読名)
├── 4_notion_md_renamed_split/ pcp 単位で分割した Markdown
├── 5_zip_batches/             初回実行時の zip バッチ
├── 5_zip_batches_diff/        incremental_export が生成する差分 zip バッチ
├── 6_report/                  対応表 CSV など分析成果物の置き場所
│   └── filename_mapping.csv
└── _snapshot/                 差分検出用スナップショット (管理用、番号なし)
```

`3_notion_md_renamed/` 内のファイルは `{YYYY-MM-DD}__{安全化タイトル}__{conv_id 先頭 8 文字}.md` の形式に従います。たとえば `2025-12-19__GitHubの使い方__abc12345.md` のようになります。これにより、Notion インポート後も内容を一目で識別できます。`6_report/filename_mapping.csv` には、旧名 (UUID 系) と新名 (可読) の対応が記録されており、後から追跡できます。

## 主要なパラメータ

- `max_pcps_per_part` (既定 25): 1 つの分割 Markdown ファイルに含める pcp の最大数。
- `target` / `overflow` (既定 100 / 20): zip バッチ 1 つあたりのファイル数の目安と許容超過。Notion の Markdown インポートのレート制限 (12 時間あたり約 120 ファイル) を踏まえた値です。
- `skip_empty` (既定 `True`): 空会話 (本文がほぼ無い削除済みチャット等) を処理対象から除外するかどうか。
- `dedupe` (既定 `True`): 同一会話内の重複した prompt-completion ペアを除去するかどうか。Claude エクスポートのツリー分岐や再生成に由来する重複に対応します。
- `shift_body_headings` (既定 `False`): 本文中の見出しレベルを 1 段繰り下げて pcp 見出しの下位に配置するかどうか。既定では本文の見出しレベルをそのまま保持します。
- `notion_safe` (既定 `True`): Notion インポート向けの安全クリーニングを適用するかどうか。通常はオンのままで問題ありません。

## 生成される Markdown の構造

各会話は次の構造の Markdown に変換されます (v0.2.0 以降の見出しベース構造、v0.4.0 で Notion 向けクリーニング自動化)。

```markdown

**A Completion by LLM**

AI の回答。

---

```

## Notion インポートの互換性 (v0.4.0 以降)

Claude のエクスポートには、`This block is not supported on your current device yet.` というプレースホルダのコードフェンスが含まれることがあります。これは Claude の UI で拡張思考ブロックやツール使用の痕跡が表示されていた箇所に対応します。Markdown にこれらが残ったままだと、コードフェンスの開閉境界がずれて、Notion のパーサがインポート全体を拒否してしまう原因となります。

v0.4.0 以降、ライブラリは Notion 用 Markdown を生成する際に、これらのプレースホルダを自動的に除去します。新規生成では、ユーザ側で特別な対処をする必要はありません。

v0.3.0 以前で生成済みの Markdown ファイルを、再生成せずに修復したい場合は、次のように呼び出します。

```python
from pyreshape_for_notion.core import clean_notion_md_folder
stats = clean_notion_md_folder(base_dir / "4_notion_md_renamed_split")
print(stats)
```

## ChatGPT 固有の処理

ChatGPT パーサには、公式エクスポートの癖に対処するための複数の処理が組み込まれています。

GPT-5 系モデルでは、1 つの回答が複数の `assistant(text)` メッセージに分割されてエクスポートされることがあります。間に `assistant(code)` や `tool` のメッセージが挟まる場合もあります。ライブラリは、連続する 2 つの user メッセージの間にあるすべての `assistant(text)` を結合します。これにより、レンダリングされた会話には冒頭の前置きだけでなく、回答全体が含まれます。

web 検索の引用を含む回答について、エクスポートは Private Use Area 文字 (`\ue200`–`\ue202`) で `cite turn{N}view{M}` のような形式のトークンを囲んで埋め込みます。これらのマーカーをそのまま残すと、Notion 上に文字化けとして表示されてしまいます。ライブラリはマーカーを除去し、各 assistant 回答の末尾に参考文献の見出しとして、引用された URL の一覧を付加します。

LaTeX 数式について、ChatGPT は標準の LaTeX デリミタ `\(...\)` および `\[...\]` を出力しますが、Notion の Markdown インポートはこれらを数式として認識しません。ライブラリはこれらを `$...$` と `$$...$$` に変換します。変換後の形式は Notion が KaTeX で正しくレンダリングします。また、ChatGPT は同じ数式を 2 度目に ```` ```tex ```` (または ```` ```latex ````) フェンスコードブロックでも出力するため、ライブラリはこの重複を除去します。

## Gemini 固有の処理

AI Chat Exporter がエクスポートする Gemini の会話ファイルでは、`---` (水平線) が次の 2 つの用途で使われています。1 つは会話の区切りとしての用途、もう 1 つは長い回答内の構造的区切り (たとえば `### 検証` や `### 結論` のような節の前) としての用途です。ライブラリは先読みによってこの 2 つを区別します。`---` の次の非空行が `## 👤 You` または `## 🤖 Gemini` である場合のみ、会話の区切りとして扱います。それ以外は、本文の一部として保持します。これにより、以前のバージョンが誤って分割し、部分的に失っていた長い Gemini 回答が正しく復元されます。

## Claude Artifacts の md を Notion へ (0.6.0 以降)

チャットのエクスポートではなく、Claude が Artifact として書き出した **単体の Markdown 文書**
(数式を多く含む論文原稿など) を Notion に取り込む場合は `artifact` サブパッケージを使います。

Notion の Markdown インポータは `$...$` / `$$...$$` を安定に解釈せず、数式スパンが本文中に
`$true$` という文字列として現れることがあります。デリミタは残り、中身の LaTeX だけが失われます。
これを避けるために二つの経路を用意しています。

### 経路 1: md → md (Import → Text & Markdown 用)

数式をコード領域へ退避します。レンダリングはされませんが、LaTeX ソースは一字も失われません。

```python
from pyreshape_for_notion import artifact

dst, stats = artifact.convert_file("CBM_axiomatic_system_syntactic_subsystem_v0_1_3.md")
print(stats.as_dict())
# {'math_inline': 270, 'math_block': 16, 'latex_delims_normalized': 0,
#  'headings_demoted': 0, 'unsupported_removed': 0, 'table_pipes_escaped': 0}
```

- インライン数式 `$x$` → `` `$x$` `` (インラインコード)
- ブロック数式 `$$...$$` → ```` ```latex ```` フェンス
- `\(...\)` `\[...\]` も同様に吸収します
- `math_mode="keep"` で数式をそのまま残せます (経路 2 の前処理用)

### 経路 2: md → Notion API ブロック (数式をレンダリングしたい場合)

md インポータを迂回し、`equation` ブロック / `equation` リッチテキストを直接構成します。
外部依存はありません。返り値は素の dict なので、`requests` でも公式 SDK でも送信できます。

```python
import requests
from pyreshape_for_notion import artifact

text   = open("CBM_axiomatic_system_syntactic_subsystem_v0_1_3.md", encoding="utf-8").read()
blocks = artifact.markdown_to_blocks(text, skip_first_h1=True)
title  = artifact.extract_title(text)

headers = {"Authorization": f"Bearer {TOKEN}",
           "Notion-Version": "2022-06-28",
           "Content-Type": "application/json"}

res  = requests.post("https://api.notion.com/v1/pages",
                     json=artifact.make_page_payload(PARENT_PAGE_ID, title, blocks),
                     headers=headers)
page = res.json()["id"]

for chunk in artifact.chunk_blocks(blocks[artifact.MAX_CHILDREN:]):
    requests.patch(f"https://api.notion.com/v1/blocks/{page}/children",
                   json={"children": chunk}, headers=headers)
```

経路 1 で退避した md も、`restore_coded_math=True` (既定) により数式へ復元されます。

**経路 3 — 直接アップロード (v0.7.0)**。経路 2 のワンストップ版です。md を読み、
ブロックを構成し、Notion API でアップロードするところまでを一つの関数で行います。
依存は標準ライブラリのみです。

```python
from pyreshape_for_notion.artifact import upload_markdown
url = upload_markdown("paper.md",
                      parent_page_id="https://www.notion.so/My-Page-24c3...",  # ページ URL のままで可
                      token="ntn_...")                                          # integration secret
```
